# 流程与定时事件

流程让团队能以可重复的方式完成任务。它有可在聊天中输入的名称，以及为该团队保存的步骤和选项。定时事件会在你选择的时间向团队聊天室发送消息。这条消息可以向小组长提问，也可以启动流程。

## 查找并运行流程

在团队聊天室输入 `/`，查看已启用的流程及其说明。选择一个流程，补充要做的事，再发送。例如，`/ask What should the export include?` 会开始讨论这项需求。交互式流程会在聊天中提问。后台流程会进入 **任务列表**。

发送后台流程命令时，**小组长** 通常根据对话编写任务说明，再把任务加入队列。如果该流程开启了 **直接起**，你的原话就是任务说明，任务会立即进入队列。内置后台流程默认关闭此选项。小组长主动提出任务时，选择 **对,做** 启动。

| 内置流程 | 使用场景与结果 |
| --- | --- |
| `/ask` | 澄清需要做的决定。每次回答一个问题，最后得到需求说明。 |
| `/plan` | 规划需要拆成多件任务的工作。读完计划和拟执行的一批任务，再选择 **全部放进任务队列**、**修改计划** 或 **暂不执行**。计划本身也是一件可跟进的任务。 |
| `/agent` | 把机械或耗时的工作交给工人。一个工人执行并报告结果，不进行审查轮次。 |
| `/write-review` | 交办实现任务并说明如何检查。写手进行实现，系统运行检查，然后写手和审查者检查结果。 |
| `/memory-tidy` | 检查团队记忆，移除失去价值的条目并合并重复条目。交付单列出操作以及需要你决定的建议。条目需要处理时，团队也可自动运行此流程，24 小时内最多一次。 |
| `/docs-tidy` | 重新检查受改动影响的文档，并轮流抽查其余文档。交付单分别列出机械性修正和需要你回答的问题。 |
| `/code-sweep` | 检查代码中可以清理的地方。阅读交付单中带编号的建议，告诉小组长要执行哪些。扫描本身是只读的。 |
| `/write-flow` 和 `/edit-flow` | 描述可重复的任务来创建流程，或说明如何更改现有流程。结果会保存到你的团队。 |

## 选择写手和审查者

打开团队聊天室里的 ⋯，选择 **团队流程**，再打开 `/write-review`。页面显示步骤和此团队今后运行任务时使用的选项。

| 选项 | 用法 |
| --- | --- |
| **谁写** | 保留 **自动**，按任务难度选择提供商，也可为撰写步骤指定引擎。 |
| **谁审** | 保留 **自动**，寻找不同模型系列的独立审查者，也可为审查指定引擎。写手负责自审。具体使用的模型由团队模型设置决定。 |
| **自审遍数** | 可选 0–10，默认 3。每轮由写手检查工作、修正发现的问题并复查，直到未发现问题或达到次数上限。设为 0 可跳过自审。 |
| **最多几轮** | 可选 0–10，默认 6。设为 0 即为 Solo，跳过独立审查，保留自审设置。 |

发现 P1 问题时，须再次审查整个改动。较轻的问题只需审查修正。从第 3 轮起，如果没有 P1 问题，写手可以做完剩余修正后直接交付。达到轮数上限时若仍有 P1 问题，请打开 **交付单** 查看导致任务停止的问题。

要合并代码，最后一次提交必须通过所有适用的完整检查。如果只改动文档且没有适用检查，须由独立审查者认可这一理由。在 Solo 中，没有可运行检查的改动会保持 **未完成**。[查看任务的检查与交付单](jobs.md)

## 编写或编辑团队流程

1. 在团队聊天室发送 `/write-flow`，随后写明步骤、完成条件、某一步失败时怎么处理，以及要交付什么。例如，`/write-flow List Markdown files changed since the last commit. Report their paths. If none changed, say so.`。
2. 如果写手需要你决定，请在聊天中回答。流程写好并检查后，聊天会显示保存时使用的名称。选择 **看流程** 查看说明、步骤和选项。该名称现在可在 `/` 菜单中使用。
3. 要修改流程，选择 **在聊天中编辑** 或发送 `/edit-flow <name> <change>`。说明要改什么、保留什么。编辑自定义流程会替换团队中的该版本。编辑内置流程会用不同名称创建自定义流程。阅读交付单，核对实际生效的选项值及编辑时移除的步骤规则。

你也可以在流程详情页编辑选项。如果流程使用一套已保存的指令，你可以在那里修改指令，供下次运行使用。关闭 **启用** 后，团队菜单不再提供此流程供新任务使用。已排队和正在运行的任务可以完成。两条编写流程的命令仍可使用。

## 定时发送消息

1. 在团队 ⋯ 菜单中打开 **定时事件**，使用加号按钮 **添加事件**。在 **要说的话** 下输入要发送的消息，最多 16 KiB。例如，`/docs-tidy Check the project documentation.`。
2. 选择 **频率**。要在将来的本地日期和时间发送，选 **一次性**；每天某个时间发送选 **每天**；周一至周五发送选 **工作日**。选择 **每隔几分钟** 时，将 **重复间隔(分钟)** 设为 5 到 720。用 **从** 和 **到** 将运行时间限定在一天中的某个时段。
3. 核对 **时区**，初始值为浏览器的时区，然后保存。列表会显示消息首行和下次运行时间。创建事件即授权发送消息。到时会以你的名义在聊天中发送，并标为 **定时**。每次触发都会占用完整的一轮小组长对话。

时间以所选时区为准。若夏令时切换跳过了预定时刻，事件会使用下一个有效时刻。若同一时刻出现两次，采用第一次。为间隔事件设置时段后，时段外的触发会被跳过。

打开事件即可编辑消息或时间。保存后会重新计算下次运行时间。停用事件可停止日后发送，想恢复时再启用。重新启用后从当时开始安排。调度服务中断后，只会补发最近一次错过的消息。可以按文本或确切编号（如 `#6`）搜索事件。使用 **已跑完** 查找已结束的一次性事件。

## 遇到问题时

- 如果聊天不识别流程，输入 `/`，查看为该团队启用的名称。需要时在 **团队流程** 中重新启用流程。如果因 `/write-review` 已停用而无法把计划中的一批任务加入队列，请先启用再提交。
- 每个团队最多可有 30 个自定义流程。达到上限后，先删除不需要的流程，再创建新流程。若名称已被占用，可以编辑同名流程或选择新名称。如果编辑结果提示被移除的步骤规则太长，无法写入交付单，请在流程页缩短或移动该规则，再试一次。
- 每个团队最多可有 20 个定时事件。达到上限后，先删除一个再添加。如果一次性事件已运行，要再运行就需重新创建。请选择未来的时间，并使用上述范围内的间隔。
- 如果定时消息指定的流程缺失或已停用，或指定的编号条目不存在，则本次触发已消耗。请在下次触发前更正消息或启用流程。若定时触发的交互式流程提示另一个流程正在忙，它会等到后续触发。
