# フローと定時イベント

フローは、チームが同じ手順で作業を繰り返すためのものです。チャットで入力できる名前があり、手順とオプションはチームごとに保存されます。定時イベントは、指定した時刻にチームチャットへメッセージを送ります。そのメッセージでリーダーに質問したり、フローを始めたりできます。

## フローを探して実行する

チームチャットで `/` と入力すると、有効なフローと説明が表示されます。フローを選び、依頼内容を追加して送ります。たとえば `/ask What should the export include?` と送ると、その要件についての会話が始まります。対話型のフローはチャットで質問します。バックグラウンドのフローは **作業一覧** に入ります。

バックグラウンドのフローコマンドを送ると、通常は **リーダー** が会話をもとに作業内容をまとめ、キューに入れます。そのフローで **直接開始** がオンなら、入力した言葉がそのまま作業内容になり、すぐにキューに入ります。組み込みのバックグラウンドフローでは既定でオフです。リーダーが自ら作業を提案した場合は、**はい、実行** を選ぶと始まります。

| 組み込みのフロー | 使い方と結果 |
| --- | --- |
| `/ask` | 決めるべきことを明確にします。質問に 1 つずつ答えると、要件の概要が得られます。 |
| `/plan` | 複数のタスクが必要な作業の計画を立てます。計画と提案されたタスクの一覧を確認し、**すべてキューに追加**、**計画を修正**、**今は実行しない** のいずれかを選びます。計画を立てる作業自体の進捗も確認できます。 |
| `/agent` | 機械的な作業や時間のかかる作業をワーカーに頼みます。ワーカー 1 人が実行し、レビューのラウンドを行わずに結果を報告します。 |
| `/write-review` | 実装作業と確認方法をチームに伝えます。書き手が作業し、チェックが実行され、書き手とレビュー担当が結果を確認します。 |
| `/memory-tidy` | チームメモリを確認し、不要になった項目を削除して重複をまとめます。納品レポートには、実行した操作と判断してほしい提案が並びます。見直しが必要な項目があれば、チームは 24 時間に 1 回まで自動で実行できます。 |
| `/docs-tidy` | 変更の影響を受ける文書を再確認し、残りも順番に抜き取り確認します。納品レポートでは機械的に直した点と、確認したい質問を分けて示します。 |
| `/code-sweep` | 整理できる箇所がないかコードを点検します。納品レポートで番号付きの提案を読み、実行するものをリーダーに伝えます。点検は読み取り専用です。 |
| `/write-flow` と `/edit-flow` | 繰り返す作業を説明してフローを作るか、既存のフローの変更内容を説明します。結果は自分のチームに保存されます。 |

## 書き手とレビュー担当を選ぶ

チームチャットで ⋯ を開き、**チームのフロー** を選び、`/write-review` を開きます。このチームで今後実行する作業のステップとオプションが表示されます。

| オプション | 使い方 |
| --- | --- |
| **誰が書くか** | **自動** のままにすると難易度に応じて提供元が選ばれます。書くステップで使うエンジンを指定することもできます。 |
| **誰がレビューするか** | **自動** のままにすると、別のモデル系列から独立したレビュー担当を探します。レビュー用のエンジンを指定することもできます。自己レビューは書き手が行います。実際のモデルはチームのモデル設定で決まります。 |
| **自己レビュー回数** | 0～10 回、既定は 3 回です。ラウンドごとに、書き手が作業を確認して指摘を直し、指摘がなくなるかこの回数に達するまで確認を繰り返します。0 に設定すると自己レビューを省きます。 |
| **最大何ラウンド** | 0～10 ラウンド、既定は 6 です。0 では Solo になり、独立レビューを省いて自己レビューの設定を維持します。 |

P1 の指摘があれば、変更全体を再レビューします。それより軽い指摘の場合は、修正箇所をレビューします。第 3 ラウンド以降、P1 がなければ、書き手は残りの修正を終えて再レビューなしで納品できます。ラウンド数の上限で P1 が残っている場合は、**納品レポート** を開き、作業を止めた指摘を確認します。

コードをマージするには、最終コミットで該当するチェックをすべて通す必要があります。文書だけの変更に該当するチェックがない場合は、独立したレビュー担当がその理由を認める必要があります。Solo で実行できるチェックがない変更は **未完了** のままになります。[作業のチェックと納品レポートを読む](jobs.md)

## チームのフローを作成または編集する

1. チームチャットで `/write-flow` に続けて、手順、完了の条件、ステップが失敗した場合の対応、納品するものを書いて送ります。たとえば `/write-flow List Markdown files changed since the last commit. Report their paths. If none changed, say so.` と送ります。
2. 書き手が判断を必要とする場合は、チャットの質問に答えます。フローの作成とチェックが終わると、保存した名前がチャットに表示されます。**フローを見る** を選ぶと、説明、ステップ、オプションを読めます。`/` メニューからその名前を選べるようになります。
3. フローを変更するには、**チャットで編集** を選ぶか、`/edit-flow <name> <change>` と送ります。変更するものと維持するものを伝えます。カスタムフローを編集するとチームの版が置き換わります。組み込みのフローを編集すると別名のカスタムフローが作成されます。適用されたオプション値と編集で除かれたステップのルールは、納品レポートで確認します。

フローの詳細画面でもオプションを編集できます。保存済みの指示に従うフローなら、その指示を次回の実行に向けて編集できます。**有効** をオフにすると、チームのメニューでそのフローの新しい実行を開始できなくなります。待機中と実行中の作業は完了できます。フローを作成・編集する 2 つのコマンドは引き続き使えます。

## メッセージの送信を予約する

1. チームの ⋯ メニューで **定時イベント** を開き、プラスボタンで **イベントを追加** を選びます。**伝えたいこと** に、送りたいメッセージを 16 KiB まで入力します。たとえば `/docs-tidy Check the project documentation.` と入力します。
2. **頻度** を設定します。今後の現地日時を指定するには **1回のみ**、毎日同じ時刻に送るには **毎日**、月曜日から金曜日まで送るには **平日** を選びます。**数分ごと** では **間隔（分）** を 5～720 の範囲で設定します。1 日の一部の時間帯に限るには、**開始** と **終了** を指定します。
3. ブラウザーの設定が初期値になっている **タイムゾーン** を確認し、保存します。一覧にメッセージの先頭行と次回の実行時刻が表示されます。イベントの作成によって、メッセージの送信を承認します。設定時刻になると自分の名前でチャットに送信され、**定時** の印が付きます。1 回の送信ごとにリーダーのターンを 1 回分使います。

時刻は選んだタイムゾーンに従います。夏時間への切り替えで予定時刻が飛ばされた場合は、次の有効な時刻を使います。同じ時刻が繰り返される場合は、最初の時刻を使います。時間帯を指定した間隔イベントでは、時間帯外の実行が省かれます。

イベントを開くとメッセージやスケジュールを編集できます。保存すると次回の実行時刻が再計算されます。今後の送信を止めるには無効にし、再開するときに有効にします。再度有効にした時点から予定が組まれます。スケジュール機能の中断後は、送れなかったうち最新の 1 件だけが送信されます。テキストか、`#6` のような正確な番号でイベントを検索できます。終了した 1 回限りのイベントは **実行済み** で探します。

## うまくいかないとき

- チャットでフローが認識されない場合は、`/` と入力してこのチームで有効なフロー名を確認します。必要なら **チームのフロー** でフローを再度有効にします。`/write-review` が無効で計画のタスクを一括でキューに入れられない場合は、有効にしてから作業を送り直します。
- チームごとにカスタムフローを 30 個まで作れます。上限に達したら、使わないカスタムフローを削除してから作成します。名前がすでに使われている場合は、そのフローを編集するか、別の名前を選びます。編集で外したステップのルールが長すぎて納品レポートに含められない場合は、フローの画面でルールを短くするか移動してからやり直します。
- チームごとに定時イベントを 20 件まで登録できます。上限に達したら、イベントを削除してから追加します。1 回限りのイベントがすでに実行された場合は、新しいイベントを作成して繰り返します。未来の時刻と、上記の範囲内の間隔を指定してください。
- 予約メッセージが、存在しないか無効なフローや、存在しない番号の項目を指している場合、その回は消化されます。次の実行時刻までにメッセージを直すか、フローを有効にします。予約された対話型のフローが別のフローの実行中と報告した場合は、後の実行機会を待ちます。
